# Wesal

This project uses the **axiom** spec-driven development plugin. The full spec lives in `docs/`. Always read `docs/PRD.md` and `docs/INDEX.md` first to orient.

## Working with axiom

Use `axiom:*` skills for all spec/doc-related work — they keep docs alive and consistent.

| Goal                        | Skill            |
| --------------------------- | ---------------- |
| Implement a roadmap section | `/axiom:section` |
| Add or change requirements  | `/axiom:amend`   |
| Fix a bug                   | `/axiom:fix`     |
| Project status              | `/axiom:status`  |
| Find where X is documented  | `/axiom:where`   |
| Audit doc consistency       | `/axiom:doctor`  |

Full skill catalog: see the axiom plugin's `framework/system-preamble.md`, or run `/axiom:status`.

## Rules

1. Read `docs/INDEX.md` first to find what's relevant — don't load the whole spec tree.
2. **Don't hand-edit `docs/INDEX.md`** — it's regenerated by `axiom:reindex`.
3. Use `axiom:*` skills for changes; they run the sync procedure automatically.
4. If you change code that affects spec'd behavior, run `/axiom:amend` (or `/axiom:fix`) to keep docs in sync.
5. The spec is the source of truth for _intent_. Code is the source of truth for _what currently exists_. When they disagree, reconcile — don't ignore.
6. Memory is authoritative for nothing. When a note in `docs/memory/` contradicts a spec or the code, the note is what's wrong — retire it with `/axiom:remember --forget`.
